# Releasing bsv-tracker

1. Every change is born on `beta` (the owner's ruling of 2026-11-18; the stack's record `docs/DECISIONS-2026-10-19.md`, section 31.1) and lands there through a pull request; nothing is pushed to either line directly. `main` is the stable line and takes a stable roll-up and nothing else (the direction rule below), and `beta` merges into it once, at the cut, on the owner's tag (point 16).
2. A pull request is green on its line's required checks: `test`, `fmt`, `clippy`, `vectors`, `wasm32`, `locks`, and `main-in-beta` on `beta` or `beta-born` on `main`.
3. A version is set by one commit: `version` in `Cargo.toml` (and `Cargo.lock`) and the `CHANGELOG.md` heading. On `beta` it is a prerelease's (point 11); on `main` it is a roll-up's version commit (point 13).
4. Merge by rebase (linear history), never by squash: a squash drops each pick's `(cherry picked from commit <sha>)` line. The owner's account merges its own PR. The one merge commit is the cut's (point 16).
5. Tag the landed version commit on its line: `git tag vX.Y.Z <sha> && git push origin vX.Y.Z` (the tag ruleset lets the owner alone create `v*`).
6. `.github/workflows/release.yml` checks the tag against `Cargo.toml` and its line (`main`; a prerelease `beta`, point 11), reruns the checks, and publishes.
7. Nothing publishes from a laptop and no crates.io token is stored anywhere, with one recorded exception: the birth publish of 0.1.0 came from the captain's machine with the token, because crates.io creates a trusted-publishing entry only for a crate that already exists; the entry was created the minute after, and every later version publishes from the tag.
8. crates.io Trusted Publishing names owner `Calhooon`, repository `bsv-tracker`, workflow `release.yml`, no environment.
9. Every action in the two workflows is pinned by commit sha; a bump is its own PR, the sha read with `git ls-remote`.
10. The door opened on the owner's word of 2026-10-09 ("tracker public"): the repository is public, the branch protection and the two tag rulesets are on, and 0.1.0 is on crates.io.
11. A prerelease is cut from `beta`'s tip, never from `main`: the release PR into `beta` sets `version` to `X.Y.Z-beta.N` in `Cargo.toml` (and `Cargo.lock`) with its `CHANGELOG.md` heading, merges green, and the landed commit on `beta` is tagged `vX.Y.Z-beta.N`. It carries everything `beta`'s tip holds: nothing on `beta` is reverted and landed again so that a prerelease carries a pin alone. `release.yml` admits a tag whose version holds a `-` only when its commit is on `beta`, any other tag only on `main`, and publishes either. A prerelease pins its bsv-rs prerelease exactly (`=X.Y.Z-beta.N`, since a caret requirement admits no prerelease), and its dependents (bsv-wallet-toolbox-rs's and bsv-wallet-cli's beta lines) pin this crate's prerelease exactly too, so the lock of each holds one bsv-rs.

## The direction rule (the owner's ruling of 2026-11-18)

Every change is born on `beta`. `main` takes only a quick fix of six classes, the six of bsv-rs's and bsv-wallet-cli's `RELEASING.md`, "The direction rule":

- a security advisory (of this crate, or of a crate it pins);
- a panic on input;
- a wrong verdict: a wrong word for a transaction, or a proof or a header judged wrongly;
- a break in a live dependent (bsv-wallet-toolbox-rs, bsv-wallet-cli);
- the front pages (the fifth class): here `README.md`, the page crates.io and GitHub show for the stable line (this repository has no `SECURITY.md` and no folder of release notes). `main` takes each such commit of `beta` by `git cherry-pick -x`, resolved to what `main`'s tree proves: a sentence whose matter `main` lacks is cut from `main`'s README, and a section of `beta`'s alone stays `beta`'s;
- a toolchain mend (the sixth class): a mend that a required check on `main` demands after a release of CI's toolchain, with no behaviour change, taken by `git cherry-pick -x` of the `beta` commit that mended the same line.

12. Every commit of `main` is a `git cherry-pick -x` of a `beta` commit with its test; the `(cherry picked from commit <sha>)` line is the link both checks read, kept through a hand resolution. The pull request into `main` says its class in one line of its body: `Class: security advisory`, `Class: panic on input`, `Class: wrong verdict`, `Class: break in a live dependent`, `Class: front pages` or `Class: toolchain mend`. Two shapes are born on `main` by nature and the checks let them through, saying so: a hop commit (`Cargo.lock`, and `Cargo.toml`'s `bsv-*` requirement lines, nothing else; the dependency bot's `deps(stack)` commits on `main`, `Cargo.lock` alone, are hop commits) and a version commit (`Cargo.toml`'s and `Cargo.lock`'s `version` and `CHANGELOG.md`'s section, nothing else).
13. A stable roll-up, in order: each fix lands on `beta` with its test and its `CHANGELOG.md` entry; on a branch from `origin/main`, `git cherry-pick -x` of each (an entry's conflict resolved to main's `## [Unreleased]`); the version commit, which puts the heading above those entries; the pull request into `main` with its class line, green, rebase-merged; the tag on the owner's word; then the link. Quick fixes travel together, and a dependent hops once per roll-up.
14. The link: one pull request into `beta`, `CHANGELOG.md` alone, the released section as `main` words it placed above the previous stable section, its commit carrying the version commit's `(cherry picked from commit <sha>)` line. `beta` keeps its version and its Unreleased. `main-in-beta` holds `beta` until it lands.
15. The checks (`.github/workflows/lines.yml`, `.github/ci/lines.sh`, proved by `.github/ci/test_lines.py`; the same bytes on both lines, and bsv-wallet-cli's but for `lines.yml`'s baseline and its note on the merge queue this repository lacks). A commit is on a line by sha, by patch (`git cherry`), or by a cherry-pick line in either direction. `beta-born`, on every pull request into `main`, asks it of the pull request's commits against `origin/beta`, a hop commit and a version commit let through. `main-in-beta`, on every pull request into `beta` and every push to `beta`, asks it of each commit of `origin/main` after the baseline (`MAIN_BASELINE`: `86f193b8`, the merge base of `main` and `beta`, where the lines parted, so nothing is waived), a hop commit let through.
16. The cut. `beta` merges into `main` once per minor, on the owner's tag. In order: (a) the last pull request into `beta` is the version commit `X.Y.0`, the stable version and the stable bsv-rs requirement; (b) `main-in-beta` is green on `beta`'s tip and `beta`'s `CHANGELOG.md` holds every `## [...]` heading `main`'s holds; (c) a branch `cut/X.Y.0` from `origin/beta` takes `git merge -s ours origin/main`, so its tree is `beta`'s tree and its history holds both lines; (d) its pull request into `main` is the one pull request that lands as a merge commit, by the owner's hand (the linear-history requirement on `main` lifted for that merge and restored after it); (e) the tag `vX.Y.0` on that merge commit; (f) on `beta`, the next pull request sets the next prerelease version and moves `MAIN_BASELINE` to the cut's merge commit.
17. On a day a fix cannot land on `beta`: the owner alone may take `beta-born` out of `main`'s required contexts for that one pull request and put it back in the same sitting; the fix lands on `beta` next, carrying the main commit's cherry-pick line, and `main-in-beta` holds `beta` until it does.
18. The default branch's copy of a workflow. GitHub runs a dispatched workflow from the default branch's file, so `main` carries a copy of `.github/workflows/dependabot-automerge.yml`. A change to it is born on `beta`; `main`'s copy takes it by `git cherry-pick -x` of that `beta` commit, in a pull request whose commits touch workflow files and nothing else and whose body says `Class: none; the default branch's copy of a workflow`. The file is named here; another is added by a pull request into `beta` that changes this point.
19. This repository keeps no HANDOFF.md: its captain's record is bsv-wallet-cli's HANDOFF.md, on that repository's `beta`.
